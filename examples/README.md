# Candidate comparison workflow

This stage **does not execute candidate code**. It combines JSON test reports produced by `evaluator.runner` into a comparative table with provenance fields and an empty human-review rubric.

```bash
python -m evaluator.compare examples/candidates.example.json \
  --json-output reports/example-comparison.json \
  --markdown-output reports/example-comparison.md
```

The committed fixtures are **hand-authored baseline/reference examples**, not model outputs or independently measured model performance. Replace them with real per-candidate result JSON files only after evaluating candidates in a restricted container/VM. The existing runner is not a security sandbox; its timeout does not prevent malicious code execution.

Manifest fields: `id`, `task`, `report` (path relative to manifest), and `source` are required. Optional fields: `model`, `model_version`, `prompt_sha256`, `notes`. Never label a human-written or synthetic candidate as generated by a model. For real AI evaluation, preserve the exact prompt, generation settings, output SHA, model identity, and evaluation environment; review code quality manually. The comparison utility preserves provenance metadata but does not verify its authenticity.

Human review fields (`correctness`, `edge_cases`, `maintainability`, `explanation_quality`) are set to `null` until an assessor actually performs a review. Automated test pass rate should never be presented as a complete quality score.
